**Blocking**

The R2 blocking finding (B1-R2) is fixed as described. `DecisionQueue.tsx:218` now derives `viewedStatus` from `statusForPair([selectedRecord], sessionId, selectedCandidate.id)` and drives both the `--active` class and `aria-pressed` from it (`:219-220`), so the editor renders the viewer-facing orientation. **Non-blocking**

- **N1-R3 — `createReviewRecord` trims but does not validate, so the write path can mint a record that `validateReviewRecord` will later reject.** `records.ts:149-166` trims `leftSessionId`/`rightSessionId`/`recordId` (R2/N5 addressed, `tests/records.spec.ts:50-55`), but does not enforce non-empty ids or `left !== right`, and `ReviewStore.write` (`storage.ts:137-160`) serializes without re-validating. A whitespace-only or empty session id from the host would therefore be persisted, then fail `validateReviewRecord` (`records.ts:102-104`) on the next load, and — because R3 now blocks writes on *every* parse failure (`storage.ts:131-134`) — put the store into the terminal fail-closed state until an explicit import. The two changes are individually correct but compose into a self-poisoning path. Not reachable from current wiring: candidates come from `findRelatedSessions` (`lineage.ts`), which excludes self-pairs, and ids come from `SessionListState.byId`. `tests/records.spec.ts:34-35` demonstrates the underlying asymmetry (a constructed whitespace-`recordId` record serializes but fails to parse).
- **N2-R3 — `update()` returns a truthy record when the write failed.** `storage.ts:90-95` returns `updated` on success and `existing` on failure. The notice's claim ("no longer report unpersisted results as success") holds in the sense that the returned object always reflects persisted state, but a caller testing truthiness cannot distinguish failure from success. `ensureRecord` (`:82-88`) is stricter, returning `undefined` when `write` fails — the two APIs signal failure differently. `DecisionQueue.tsx:113`/`:124` discards both return values, so no product-visible effect today.
- **N3-R3 — the `storageArea` filter has a `null` hole.** `storage.ts:46` returns early only when `event.storageArea !== null`; an event with `storageArea === null` still reaches the `key === null` and `newValue === null` branches (`:47-59`), which reset `current.records` to `[]` *and* clear `writesBlocked`, even for a store backed by a non-`localStorage` `StorageLike`. Real browsers populate `storageArea` on genuine events, so R2/N3's main scenario (`sessionStorage.clear()` wiping our snapshot) is closed; the residue is synthetic/jsdom-dispatched events. The comparison is written through a cast (`event.storageArea !== (this.storage as StorageLike | undefined)`), which is sound at runtime but silences the type mismatch rather than modelling it.
- **N4-R3 — `read-failed` is the one load failure that does not block writes.** `storage.ts:121-127` sets the error and returns without setting `writesBlocked`, so a subsequent `ensureRecord`/`update` will `setItem` over storage whose contents were never read. Narrow (a throwing `getItem` normally implies a throwing `setItem`), but it is the remaining half of R2/N1.
- **N5-R3 — fail-closed recovery is destructive and export is still unavailable while blocked.** `importJson` (`:97-108`) passes `allowBlocked = true`, merging into `current.records`, which is `[]` after a failed load; the unparseable or oversized original is overwritten with no backup key. Meanwhile `exportJson` (`:110-112`) serializes the empty in-memory set, so the preserved-on-disk data still cannot be extracted through the product (R2/N2 is now escapable but only by discarding). This is the declared design and is user-initiated behind a visible `storageError` notice (`DecisionQueue.tsx:236`), so it is recorded rather than escalated.
- **N6-R3 — candidate option labels render the raw status token untranslated.** `DecisionQueue.tsx:179-180` interpolates `candidateStatus` directly (e.g. `· keep-left`) while the queue row (`:206`) maps through `STATUS_LABELS`/`t`. Orientation is correct on both paths; this is an i18n/consistency wart only. `docs/browser-gate-receipt.json:44` corroborates the raw form in real rendering.
- **N7-R3 — `cleanText` is not strictly idempotent at the truncation boundary.** `records.ts:57-59` trims then slices; a tag longer than 32 chars whose 32nd character is whitespace yields a value with trailing space in memory that will be trimmed again on reload, so the serialize/parse round-trip can silently alter a tag. Cosmetic drift, not a validation failure. Carried forward with R2/N8 (all-or-nothing migration, silent normalization, truncation before `new URL()`).
- **N8-R3 — orientation is exact-string-matched in the UI read path.** `queue.ts:25-33` (`recordForPair`) compares ids verbatim while `ReviewStore.ensureRecord` (`storage.ts:83`) compares canonical trimmed `pairKey`s. With an untrimmed host id the store would find an existing record while the UI would not, degrading to `t('noRecord')`. It fails safe (no inverted status is displayed, because `statusForPair` returns `undefined` when `recordForPair` misses), but the two identity notions differ.

**Confirmed fixed / no regression found (within scope)**
