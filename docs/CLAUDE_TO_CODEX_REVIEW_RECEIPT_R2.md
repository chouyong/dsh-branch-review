## Findings

**Blocking**

- **B1-R2 (regression introduced by the canonical-pair fix) — the editor's status control renders the *stored* orientation while every other surface renders the *viewer's* orientation, so a reverse-viewed pair shows and behaves as the mirror of the truth.** `records.ts:212` now returns a canonical sorted `pairKey`, `storage.ts:78-80` (`ensureRecord`) resolves a reverse pair to the single existing record, `queue.ts:15-23` (`statusForPair`) re-orients via `invertStatus`, and `DecisionQueue.tsx:206` (queue row label) and `:179` (candidate option) correctly go through `statusForPair`. But `DecisionQueue.tsx:217` compares raw stored state: `selectedRecord.status === status` drives both the `--active` class and `aria-pressed`, with no orientation adjustment — while `updateStatus` (`:121-126`) *does* invert on write. Concrete reachable sequence: open the panel from session `A` with candidate `B` → record stored as `(A,B)`; set `keep-left` (keep `A`); open the panel from `B` with candidate `A` → `ensureRecord` correctly returns the same `(A,B)` record. The queue row for that pair now reads `keepRight` (correct for `B`'s view), while the status buttons highlight `keepLeft` — two contradictory readings of one decision in the same open panel. Worse, pressing `keepRight` from `B`'s view writes `invertStatus('keep-right') = 'keep-left'`, i.e. the stored value does not change, `aria-pressed` stays on `keepLeft`, and the button the user just pressed never becomes active: the control appears dead and the displayed decision is inverted for exactly the reverse-orientation case this commit created. Before `a68be65` this state was unreachable (each orientation had its own record); the fix closes the duplication defect and opens a display/interaction defect on the same axis. Focus item 1 asks specifically whether `UI` can produce direction errors — as written it can, and `DecisionQueue.tsx` is in this round's scope. No test covers it (see Evidence Gaps).

**Non-blocking**

- **N1-R2 — fail-closed on load is narrower than the stated intent: only `payload-too-large` blocks writes.** `storage.ts:130` sets `writesBlocked` solely for `payload-too-large`; `invalid-envelope`, `unsupported-schema`, `invalid-record` and `read-failed` leave writes enabled, so the next `ensureRecord`/`update` calls `write()` (`storage.ts:135-156`) and `setItem` replaces the intact stored payload with the post-error in-memory set. The change intent in the notice says oversized **or unparseable** snapshots become fail-closed; only the oversized half is implemented. The realistic loss channel is a forward-schema downgrade (a future `schemaVersion: 2` payload → `unsupported-schema` → overwritten by a v1 write) or externally corrupted-but-partially-valid data (`invalid-record`, which `parseReviewRecords:199` fails whole-payload). I traced round-trip stability for this version and found no path by which records written by `a68be65` become unparseable on reload (`updateReviewRecord:173` keeps `updatedAt >= createdAt`; `createReviewRecord:150` always yields a non-empty `recordId`; `findRelatedSessions:13` excludes self-pairs so `left === right` cannot be minted; `cleanText`/`cleanTags`/`cleanLinks` are idempotent), which is why I rate this non-blocking rather than blocking — the destructive path needs an external or future-version writer.
- **N2-R2 — the `payload-too-large` fail-closed state has no exit and no data path out.** `writesBlocked` is set only in `load()` and never cleared; `current.records` stays `[]`, so `exportJson()` (`storage.ts:108-110`) serializes an empty envelope and the UI (`DecisionQueue.tsx:232`) shows `storageError (payload-too-large)` with no recovery affordance. Data is preserved in `localStorage` (correct, and asserted by `tests/storage.spec.ts:49-57`) but is unreachable through the product.
- **N3-R2 — the `storage` handler ignores `event.storageArea`.** `storage.ts:46-50` treats any `key === null` event as a clear of our store. A `sessionStorage.clear()` (or a clear of any other same-origin area) dispatches `key === null`, wiping the in-memory snapshot and the error flag; the next `write()` then persists the emptied set to `localStorage`. Same gap for an injected non-`localStorage` `StorageLike`: the listener is installed whenever `window` exists (`storage.ts:44`), regardless of which storage backs the store. The `key === null` branch is otherwise the correct fix for R1A/N3.
- **N4-R2 — `ensureRecord` returns a record it failed to persist.** When `writesBlocked` or when `setItem` throws, `write()` early-returns (`storage.ts:136-152`) but `ensureRecord` still returns the freshly minted record (`storage.ts:81-83`). The caller at `DecisionQueue.tsx:76` discards the return value and re-derives via `recordForPair`, so the visible effect is the benign `t('noRecord')` empty state plus the error notice, but the API contract ("returns the record now in the store") does not hold.
- **N5-R2 — `createReviewRecord` performs no trim/validation, so the trim fix is one-sided.** `records.ts:149-163` stores `input.leftSessionId`/`rightSessionId`/`recordId` verbatim; the trim-before-check fix landed only in `validateReviewRecord` (`records.ts:96-104`, correct now — `'  '` is rejected, and whitespace-only session ids can no longer pass the `left !== right` guard). A host id carrying surrounding whitespace would therefore key differently in memory than after a reload round-trip (validator trims), which could mint a second record for the same logical pair. Not reachable from the current host wiring, where ids come from `SessionListState.byId`.
- **N6-R2 — the import lineage gate is caller-permissive for unknown sessions** (`DecisionQueue.tsx:147-152` returns `true` when either side is absent from `byId`). The store side is correctly fail-closed (`storage.ts:100-103` rejects the whole batch on any rejection, evidenced by `tests/storage.spec.ts:41-47`). Because the queue models absent sessions as a first-class `'orphaned'` bucket (`queue.ts:41`, `lineage.ts:62`), I read this as deliberate rather than a defect, and it matches the notice's "lineage eligibility unchanged" requirement. Recorded, not escalated.
- **N7-R2 — `recordHealth`'s `'degraded'` branch (`lineage.ts:61`) remains unreachable for any validated record**, and after the N1 trim fix it is now unreachable via whitespace ids too. `tests/lineage.spec.ts:42` still asserts it by direct call only. Carried forward from R1A/N5, unchanged, out of this commit's intent.
- **N8-R2 — carried forward unchanged and still non-blocking:** all-or-nothing migration with no per-record diagnostics (`records.ts:119-136`, `:197-201`); silent normalization in `cleanTags`/`cleanLinks` including truncation-before-`new URL()` (`records.ts:73-88`); `serializedByteLength`'s `raw.length` fallback undercounting multi-byte UTF-8 (`records.ts:222-229`).

**Confirmed fixed (no regression found)**

`pairKey` canonical sorting and its consistent use in `deduplicate` (`records.ts:141`) and `ensureRecord` (`storage.ts:79`); pre-write size guard closing the growth path to overflow (`storage.ts:142-145`); intact oversized snapshot preserved (`storage.ts:130`, `136-139`); trim-before-validate (`records.ts:96-104`); monotonic `updatedAt` via `Math.max(now, createdAt, updatedAt)` (`records.ts:173`); cross-tab `clear()` handling (`storage.ts:46-50`); `statusLabel` removed from `queue.ts` and absent from `src/client/index.ts:37-51`. ## Residual Risks

- If B1-R2 ships, any pair reviewed from its second session shows an inverted decision in the editor, contradicts the queue row rendered beside it, exposes a wrong `aria-pressed` to assistive technology, and makes the status buttons appear unresponsive — a user-visible correctness failure in the product's core claim of one clear decision per pair, on the exact axis this commit set out to fix, with no test that would catch it.
- N1-R2 leaves a silent, permanent data-loss channel for `unsupported-schema`/`invalid-record`/`invalid-envelope` snapshots. It is not reachable by this version's own writers as far as I could trace, but it becomes reachable the moment a newer schema version or any external editor touches the key, and a version downgrade is an ordinary user action.
- N2-R2 means the fail-closed state, once entered, is terminal from the UI: the user's data survives on disk but cannot be exported, viewed or repaired in-product.
- N3-R2 makes in-memory state sensitive to storage events from other areas; the follow-on write can then persist an emptied set. Untested cross-tab and `dispose` paths mean divergence or listener leaks would surface only in real browser use, which this round's evidence does not cover.
- Timestamp monotonicity now holds within a single record's update chain, but `now` is still host-supplied (`DecisionQueue.tsx:32-34`), so cross-device/cross-clock merge outcomes remain clock-dependent and untested.
- Scope-boundary risk: this decision covers only the five listed modules and their three listed specs. Nothing here speaks to the browser gate, bundle/package contracts, GitHub eligibility window, or release/PR readiness, all of which remain on their own ledgers.
